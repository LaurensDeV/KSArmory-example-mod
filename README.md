# KSArmory example mod

A complete KSArmory weapon pack, as small as one can be and still ship a real weapon. It adds a
**Mk 82 bomb rack**: a pylon, a 500 lb bomb, and a bombsight to release it on.

Copy this folder, rename it, replace the art, and edit `Weapons.xml`.

It also carries **a working copy of every weapon KSArmory ships**, as a pack: the Pantsir, the
rails, the guns, the sights, the YAL-1, the dispensers, the B61 rack and the MIRV bus, each with its
own parts and art under `ExampleCopy_` Ids, so it loads beside KSArmory's own. `ARSENAL.md` says
which files each one uses. It is generated by KSArmory's `tools/export-example-copy.py`; do not edit
it here.

**To fly the copy alone**, choose *KSArmory > Built-in weapons > All off* and restart: KSArmory's own
weapons stop being weapons, and every weapon in the game is this pack's. Its parts are named
`(copy)` in the editor. KSArmory's `tools/copy-save.py` turns a save's craft onto the copy's parts,
which is how its scenarios are flown against it.

**KSArmory does not know this mod exists.** It holds no list of packs: it looks in the `KSArmory/`
folder of every mod enabled in KSA's manifest and reads what it finds there — which is why installing
a pack is nothing but installing a mod.

## There is no code

That is the whole point of this folder. A weapon pack is **assets only** — no assembly, no
`[StarMap]` section in `mod.toml`, nothing to compile, no .NET SDK.

KSArmory finds the weapons by looking for a `KSArmory/` folder inside every installed mod and
reading the `.xml` files in it. It holds no list of packs and never learns this one's name; the
convention is the whole mechanism, the same way KSA discovers mods in the first place.

**A mod is a directory, so another mod's KSArmory content lives in a folder named after it.** The
weapons file is deliberately *not* listed in `mod.toml`'s `assets` array — KSA hands every entry
there to its own asset-bundle loader, which would parse it with the wrong reader.

If you do want code — building definitions at runtime, reacting to something — a pack can ship an
assembly and call `KSArmory.Armoury.Register(xml, "YourModId")` from `[StarMapBeforeMain]`
instead. It takes a string rather than a profile, so even then you need only `KSArmory.dll` and
`StarMap.API.dll` and no game assemblies. Most packs will never need it.

## What is in the folder

| | |
| --- | --- |
| `mod.toml` | KSA's `assets` list. No `[StarMap]` section — this mod ships no code |
| `KSArmory/Weapons.xml` | **the weapon** — read by KSArmory, never by KSA |
| `ExampleModAssets.xml` | the atlas, the material, the subparts and the part — read by KSA, never by KSArmory |
| `ExampleModGameData.xml` | mass, colliders, editor tags |
| `Meshes/`, `Textures/` | the art |
| `tools/extract-art.py` | how the mesh was lifted out of KSArmory's atlas. Run once; its output is committed |
| `KSArmory/<Family>.xml`, `ExampleCopy*.xml`, `*/ExampleCopy_*` | **the copy of KSArmory's arsenal**, generated; `ARSENAL.md` is its index |

The split is worth seeing: **`Weapons.xml` is not in `mod.toml`'s `assets` array**, and must not be.
KSA hands every entry in that list to its own asset-bundle loader, so a weapon file named there is
parsed by the wrong reader. KSArmory finds it because it is in this mod's `KSArmory/` folder.

A mod shipping only the two `*Assets.xml` files would still put the rack in the editor. It just
would not be a weapon.

## Install

```bash
./tools/deploy.sh     # copy into the KSA mods folder, register in manifest.toml
```

There is nothing to build. Copying the folder is the install.

Then launch through **StarMap**, not KSA directly.

Registering is the step people miss. KSA writes a newly discovered mod folder into `manifest.toml`
with `enabled = false` and says nothing about it, so dropping the folder in is not enough —
`deploy.sh` writes the entry for exactly this reason.

## When the part does not appear

`<KSA user dir>/Logs/KSArmory.log` names every definition that was refused and why, and once the
world has loaded it also checks that each registered part actually exists and that every subpart
marker resolves to exactly one subpart.

Check in this order:

1. **Is it enabled in `manifest.toml`?**
2. **Is the weapons file in the `KSArmory/` folder inside the mod folder?** Every `.xml` there is
   read and the name is yours to choose; one anywhere else is not read at all. KSArmory reports a pack it can see but whose mod is disabled, so a pack it
   never mentions is one it never found.
3. **Is the rack in the editor?** If not, the problem is `ExampleModAssets.xml`, not KSArmory.

## Going further

- `ARSENAL.md` — every KSArmory weapon in this same format, with the parts, meshes, textures and
  sounds behind it: guns, sights, a beam, decoys, a ballistic bus.

- `KSArmory/docs/WEAPON-PACKS.md` — every attribute a definition may carry, with the reasons.
- `KSArmory/docs/PACK-API-SURFACE.md` — the same contract generated from the code. KSArmory's
  build fails if it moves without being acknowledged.
- `KSArmory/docs/FROM-KSP-MODDING.md` — read first if you have written KSP parts. There is no
  `PartModule` here, so a part cannot *say* what it is — KSArmory recognises it by part Id instead.
- `KSArmory/.claude/skills/ksa-blender/SKILL.md` — the art contract KSA actually enforces, and the
  defects that are invisible outside the game.

## Two traps that are not yours and will still bite you

- **Never remove a `<SubPart>` from a part you have shipped.** KSA pairs a saved part with its
  current definition positionally, so removing one throws out of `Popup.DrawAll` and terminates the
  game on every save holding that part. Adding and renaming are free.
- **Markers match by case-insensitive substring, first hit wins.** `BodyMarker="Mk82"` matches the
  subpart `ExampleMod_Rack_Mk8200`, and would also match a subpart called `Mk82Cover` if one
  existed. KSArmory warns when a marker matches none or more than one.
